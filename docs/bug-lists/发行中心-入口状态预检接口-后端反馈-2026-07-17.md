# 发行中心入口状态预检接口 · 后端反馈（2026-07-17）

> 优先级：P0
> 影响范围：官网公共顶栏「发行中心」入口、新账号入驻、被邀请成员、发行方主账号、两步验证账号
> 结论：需要新增一个**只读、无副作用、可提前预取**的 App Token 接口，前端不能继续用 `byAppToken → status` 串行请求判断目标页。
> 2026-07-18 回执：后端已按本文契约实现并在 `test` 分支就绪，前端开始按回执对接。

## 一、问题现状

官网必须在用户点击「发行中心」前知道应进入哪类页面：

- 从未提交入驻：直接进入入驻申请表单。
- 待审核：进入入驻审核中状态页。
- 已驳回：进入驳回详情/重新提交页。
- 已是有效发行中心成员：进入控制台。
- 已开启两步验证的有效成员：进入两步验证页。
- 已通过但账号/成员被停用：展示明确的不可进入原因。

现有接口无法高效、无副作用地完成判断：

| 现有接口 | 缺口 |
| --- | --- |
| `GET /app/publisher/status` | 只返回申请记录和 `tb_user.is_publisher`；被邀请成员的 `isPublisher=0`、`auditStatus=null`，与全新账号无法区分。 |
| `POST /publisher/login/byAppToken` | 能识别有效成员，但职责是换取 publisher token；开启 2FA 时还会发送验证码并创建 challenge，不适合页面加载时提前调用。当前接口响应慢，点击后串行等待它再调用 `status`，用户会感觉页面卡住。 |

因此，不能通过扩展前端 fallback 或继续串行调用解决，需要后端提供独立的入口预检契约。

## 二、新接口契约

### 2.1 请求

```http
GET /app/publisher/entryStatus
token: <App token>
Accept-Language: zh | en | cht | pt
```

说明：

- 鉴权域为 App 登录态，header 与现有 `/app/publisher/status` 一致。
- 接口只查询入口所需状态，不签发 publisher token。
- 接口不得发送短信、创建 2FA challenge、写登录记录或改变任何账号状态。
- 接口不得同步调用 Swift、租户开通、短信或邮件服务。

### 2.2 成功响应

```jsonc
{
  "code": 0,
  "msg": "success",
  "data": {
    "entryTarget": "ENROLL",
    "hasActiveMember": false,
    "auditStatus": null,
    "isPublisher": 0,
    "twoFactorRequired": false,
    "rejectReason": null,
    "blockReason": null,
    "blockMessage": null
  }
}
```

字段定义：

| 字段 | 类型 | 必返 | 说明 |
| --- | --- | --- | --- |
| `entryTarget` | string enum | 是 | 权威入口目标，前端只按此字段路由，不再组合猜测其他字段。枚举见下表。 |
| `hasActiveMember` | boolean | 是 | 当前用户是否存在启用中的 `publisher_member` 身份；这是区分“被邀请成员”和“全新账号”的关键字段。 |
| `auditStatus` | `null \| 0 \| 1 \| 2` | 是 | 沿用现有口径：`null` 未申请、`0` 待审核、`1` 已通过、`2` 已驳回。 |
| `isPublisher` | `0 \| 1` | 是 | 沿用 `tb_user.is_publisher`；不能单独作为控制台准入依据。 |
| `twoFactorRequired` | boolean | 是 | 当前有效成员所属发行账户是否启用登录两步验证。该接口只告知状态，不发验证码。 |
| `rejectReason` | `string \| null` | 是 | 仅 `entryTarget=APPLICATION_REJECTED` 时有值。 |
| `blockReason` | `string enum \| null` | 是 | 稳定机器码，建议值见下表；非 `BLOCKED` 返回 `null`。 |
| `blockMessage` | `string \| null` | 是 | 按 `Accept-Language` 返回的可展示原因；非 `BLOCKED` 返回 `null`。 |

`entryTarget` 枚举：

| 值 | 前端目标 | 后端判定 |
| --- | --- | --- |
| `ENROLL` | `/distribution/enroll` 入驻表单 | 无有效成员，且 `auditStatus=null`。 |
| `APPLICATION_PENDING` | `/distribution/enroll` 审核中状态 | 无有效成员，且 `auditStatus=0`。 |
| `APPLICATION_REJECTED` | `/distribution/enroll` 驳回/重提状态 | 无有效成员，且 `auditStatus=2`。 |
| `CONSOLE` | 发行中心控制台 | 存在启用中的成员身份，且无需 2FA。 |
| `CONSOLE_2FA` | 两步验证页 | 存在启用中的成员身份，且 `twoFactorRequired=true`。 |
| `BLOCKED` | 留在当前页并展示 `blockMessage` | 已通过或曾有成员身份，但发行账户/成员已停用，或数据状态不允许进入。 |

`blockReason` 建议枚举：

| 值 | 说明 |
| --- | --- |
| `MEMBER_DISABLED` | 当前成员身份已停用。 |
| `PUBLISHER_DISABLED` | 发行账户已停用。 |
| `MEMBER_MISSING_AFTER_APPROVAL` | 申请已通过或 `isPublisher=1`，但缺少有效成员记录，需要后端核查数据。 |

## 三、状态样例

### 3.1 全新账号，未提交入驻

```json
{
  "entryTarget": "ENROLL",
  "hasActiveMember": false,
  "auditStatus": null,
  "isPublisher": 0,
  "twoFactorRequired": false,
  "rejectReason": null,
  "blockReason": null,
  "blockMessage": null
}
```

### 3.2 已提交，等待审核

```json
{
  "entryTarget": "APPLICATION_PENDING",
  "hasActiveMember": false,
  "auditStatus": 0,
  "isPublisher": 0,
  "twoFactorRequired": false,
  "rejectReason": null,
  "blockReason": null,
  "blockMessage": null
}
```

### 3.3 审核驳回

```json
{
  "entryTarget": "APPLICATION_REJECTED",
  "hasActiveMember": false,
  "auditStatus": 2,
  "isPublisher": 0,
  "twoFactorRequired": false,
  "rejectReason": "营业执照信息不清晰",
  "blockReason": null,
  "blockMessage": null
}
```

### 3.4 被邀请成员或发行方主账号，无 2FA

```json
{
  "entryTarget": "CONSOLE",
  "hasActiveMember": true,
  "auditStatus": null,
  "isPublisher": 0,
  "twoFactorRequired": false,
  "rejectReason": null,
  "blockReason": null,
  "blockMessage": null
}
```

> 被邀请成员可以是 `isPublisher=0`、`auditStatus=null`，但必须因 `hasActiveMember=true` 返回 `CONSOLE`。

### 3.5 已开启两步验证

```json
{
  "entryTarget": "CONSOLE_2FA",
  "hasActiveMember": true,
  "auditStatus": 1,
  "isPublisher": 1,
  "twoFactorRequired": true,
  "rejectReason": null,
  "blockReason": null,
  "blockMessage": null
}
```

> 此响应不发送验证码。用户实际点击进入后，前端才调用 `byAppToken` 触发发码并取得 challenge。

### 3.6 账户或成员被停用

```json
{
  "entryTarget": "BLOCKED",
  "hasActiveMember": false,
  "auditStatus": 1,
  "isPublisher": 1,
  "twoFactorRequired": false,
  "rejectReason": null,
  "blockReason": "MEMBER_DISABLED",
  "blockMessage": "当前发行中心成员身份已停用，请联系管理员"
}
```

## 四、后端实现与性能要求

1. 数据来源必须覆盖当前 App 用户、最新入驻申请、`publisher_member` 有效状态、发行账户状态和 2FA 开关。
2. `hasActiveMember` 的判定口径必须与 `POST /publisher/login/byAppToken` 当前允许换 token 的成员口径一致，避免预检说能进、实际换 token 又失败。
3. `entryTarget` 由后端统一计算并作为权威字段；前端不写 `isPublisher || auditStatus || hasActiveMember` fallback 链。
4. 只查本地数据库或缓存，不调用外部服务；建议接口 P95 小于 300ms。
5. 统一响应、401 登录失效和多语言错误文案沿用现有 App 接口规范。

## 五、前端接入方式（后端完成后）

1. 用户登录/注册成功，或官网加载时发现已有 App token：立即预取 `entryStatus`。
2. 结果按当前 App token 缓存在内存；退出、切换账号、提交入驻申请后立即失效并重新获取。
3. 点击「发行中心」时直接使用缓存的 `entryTarget` 路由，不再现场串行等待 `byAppToken → status`。
4. `CONSOLE`：进入控制台后按原流程调用 `byAppToken` 换 publisher token。
5. `CONSOLE_2FA`：直接进入两步验证目标页，再调用 `byAppToken` 触发发码并取得 challenge。
6. `ENROLL/APPLICATION_PENDING/APPLICATION_REJECTED`：直接进入 `/distribution/enroll`，页面继续使用现有 `status` 数据展示对应内容。
7. `BLOCKED`：不离开当前页，直接展示 `blockMessage`。

## 六、后端验收矩阵

| 场景 | 关键数据 | 期望 `entryTarget` | 必须无副作用 |
| --- | --- | --- | --- |
| 新账号 | 无 member、无 apply、`isPublisher=0` | `ENROLL` | 不创建 member/apply/token，不发码 |
| 待审核 | 无 member、`auditStatus=0` | `APPLICATION_PENDING` | 不修改审核状态 |
| 已驳回 | 无 member、`auditStatus=2` | `APPLICATION_REJECTED` | 不修改申请记录 |
| 被邀请成员 | active member、`isPublisher=0`、`auditStatus=null` | `CONSOLE` 或 `CONSOLE_2FA` | 不签发 publisher token，不发码 |
| 发行方主账号 | active member、`isPublisher=1` | `CONSOLE` 或 `CONSOLE_2FA` | 不签发 publisher token，不发码 |
| 成员停用 | disabled member | `BLOCKED` | 不恢复成员状态 |
| App token 失效 | 无有效 App 登录态 | 现有 401 | 不返回任何发行状态 |
