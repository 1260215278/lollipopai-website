## 1. `GET /publisher/settlement/overview` 收益总览

### 1.1 响应字段（**最终字段名以此为准**）

```jsonc
{
  "code": 0, "msg": "success",
  "data": {
    "totalCumulativeUsd": 1234.56,   // 累计实得（已扣分润）；从 publisher_earnings.creator_usd 全部加总
    "withdrawableUsd":     800.00,    // 当前可提现；= user_money.money（钱包余额，cron 入账后实时回写）
    "processingUsd":       200.00,    // 结算中（已申请待打款）；= settlement_record.creator_usd WHERE status IN (1,2)
    "withdrawnUsd":        234.56,    // 已提现（已打款）；     = settlement_record.creator_usd WHERE status = 3
    "pendingUsd":            5.00,    // 待入账（cron 跑前暂挂）；= publisher_earnings_log.creator_usd WHERE status = 0
    "yesterdayUsd":          3.20,    // 昨日实得
    "estThisMonthUsd":      18.40,    // 本月至今实得（即 monthToDate）
    "growthRate":            12.34,   // 环比%：(本月 - 上月) / 上月 × 100，保留 2 位；上月=0 时为 null
    "relatedDramas":         7,       // 产生过收益的不同剧目数（COUNT DISTINCT course_id）
    "monthlyTrend": [                 // 近 6 个月（含本月）每月实得；空月份不返回行
      { "month": "2026-01", "amountUsd": 100.00 },
      { "month": "2026-02", "amountUsd":  80.50 },
      { "month": "2026-06", "amountUsd":  18.40 }
    ],
    "currency": "USD"
  }
}
```

### 1.2 字段语义说明（必读）

| 字段 | 含义 | 数据来源 |
|---|---|---|
| `totalCumulativeUsd` | 出品方累计实得（已按 8:2/6:4 扣分润），等于历史"流水 × 分成"之和 | `SUM(publisher_earnings.creator_usd)` |
| `withdrawableUsd` | 实际可申请结算的金额（钱包余额）；逻辑上 ≈ totalCumulative − processing − withdrawn，但实际由 cron 直接落到 user_money | `user_money.money` (实时) |
| `processingUsd` | 已申请结算但未到账的金额（status 1 已申请 / 2 审核通过待打款） | `SUM(creator_usd)` from settlement_record |
| `withdrawnUsd` | 已实际打款（status 3） | 同上 |
| `pendingUsd` | 用户付费已发生但 cron 还没把 log 聚合入 publisher_earnings 的金额；当天 23:59 前看到的"今天收益" | log status=0 |
| `growthRate` | 本月（整月）vs 上月（整月）实得环比百分比；正数=增长，负数=下降；上月为 0 返回 `null`（前端展示"--"） | 计算字段 |
| `relatedDramas` | 不区分剧的语言/上下架，凡有过 publisher_earnings 行的剧都算 | `COUNT(DISTINCT course_id)` |
| `monthlyTrend` | 时间升序；金额是 creator_usd 月汇总；空月份**不补 0**，前端如要画图需自行补齐 | 一条 SQL `GROUP BY DATE_FORMAT(earn_date,'%Y-%m')` |

### 1.3 缓存

返回 60s Redis 缓存（key 由 `PublisherSettlementCacheBuster.key()` 决定）。
当 cron 重新入账后 cache_buster 会失效旧 key（已有机制）。前端不需主动刷。

## 2. `GET /publisher/settlement/earnings` 收益明细（分页）

### 2.1 入参

```
?page=1&limit=10&startDate=2026-06-01&endDate=2026-06-30&courseId=1024
```

`startDate/endDate` 格式 `yyyy-MM-dd`；`courseId` 可空。

### 2.2 响应字段

```jsonc
{
  "code": 0, "msg": "success",
  "data": {
    "totalCount": 42,
    "list": [
      {
        "earnDate":     "2026-06-29",  // String yyyy-MM-dd，按日聚合，不按月
        "courseId":     1024,
        "courseTitle":  "山姆短剧001",
        "courseImg":    "https://oss.../cover.jpg",
        "publishScope": 2,             // 1账号主页 / 2全量推荐
        "ratioLabel":   "6:4",         // creator:platform（1→"8:2"; 2→"6:4"）；publishScope 缺失时为 null
        "orderCount":   12,            // 当日订单数（购买/订阅累计笔数）
        "grossUsd":     50.00,         // 当日总流水
        "creatorUsd":   30.00,         // 当日出品方实得（=grossUsd × creatorRatio%）
        "ratio":        60             // 当日最大分成比（创作者占百分比 80 或 60），从 log 取 MAX
      }
    ]
  }
}
```

### 2.3 关于「状态」

**每行没有 status 字段**——本表是"已实现的日收益"，按定义已结算入账（要不就在 `pendingUsd` 里没进来）。

「已结算/结算中/待结算」语义在**结算单**层（`/publisher/settlement/records`），不在收益明细。两者关系：
- 收益明细行 = 一笔笔已入账的"账面收入"
- 结算单 = 把若干天的账面收入打包向运营申请提现

前端结算页若要同时展示"该日收益是否已申请提现"，需要做"earnings + records 时间区间叠加"的合并展示（v1 不做）。

### 2.4 关于「收益类型」

`publishScope` 取代「收益类型」枚举：
- `1` → 账号主页（仅展示在出品方主页，分成 8:2）
- `2` → 全量推荐（进入平台首页/分类流，分成 6:4）

如需文案，前端按 i18n 自行渲染（建议 key：`revenue_type_personal_homepage` / `revenue_type_full_distribution`，本期不入库，前端硬编码或本地 i18n 即可）。

## 5. 遗留确认项答复

### 5.1 结算单 `accountSnapshot` 结构

申请结算时把 `PublisherPayoutAccount` Jackson 序列化整体落入。结构：

```json
{
  "id": 1,
  "publisherUserId": 12345,
  "companyName": "山姆短剧工作室",
  "accountNo": "6225XXXX0000",
  "bank": "招商银行",
  "branch": "深圳分行",
  "accountHolder": "张三",
  "currency": "USD",
  "status": 1,
  "createTime": "2026-06-30 12:00:00",
  "updateTime": "2026-06-30 12:00:00",
  "isDelete": 0
}
```

字段含义同收款账号实体（见综合契约 §6.3）。**这是 string 类型字段**（DB 里 TEXT），前端拿到后**自行 `JSON.parse()`**。空字符串/null 都表示"未申请"或"申请时账号丢失"（理论不应发生，监控用）。

后管结算单审核展示建议：账号脱敏显示（如 `6225 **** **** 0000`），便于运营核对。

### 5.2 `emailRegister.sysPhone` web 端

**web 端可省略**（不传或传 null 都行）。

`sysPhone` 在后端代码里只是写入 `tb_user.sys_phone` 列作归因统计（用于推广/分析），**无业务逻辑依赖**。源是 mobile-only 的"1=Android / 2=iOS"，web 端没有对应取值。

如果一定要传，建议传字符串 `"3"`（约定 web 端归因码）；但**不建议**——保持空值在统计里更容易区分 web 来源。
