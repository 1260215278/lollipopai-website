## 0. 路径前缀与 token 总图（**先看这里**）

发行中心相关接口分布在 **3 个鉴权域**，前端务必区分：

| 域 | 路径前缀 | 鉴权 | header 取值来源 |
|---|---|---|---|
| **App 端**（C 用户域） | `/app/**` | App JWT（`@Login`） | App 登录接口返回的 `token`（顶层） |
| **管理端**（后管） | 非 `/app`、非 `/publisher` | Shiro `oauth2` | `/sys/login` 返回的 token |
| **发行中心**（出品方控制台） | `/publisher/**` | 独立 publisher JWT（`@PublisherLogin`） | `/publisher/login/byAppToken` 用 App token 换得 |

**前端反馈里把结算/收款接口路径写成 `/app/publisher/...`，那个路径前缀错了。** 正确路径见 §6。

入驻流程对外公开 + 入驻完毕换 publisher token 的链路保持不变：
1. App 登录 → 拿到 App token；
2. （已开通的）`POST /publisher/login/byAppToken?appToken=<App token>` → 拿到 publisher token；
3. 之后所有 `/publisher/**` 用 publisher token。

## 1. §1 登录契约（bug 2 / 4 / 5）—— 澄清

代码核对：`AppLoginController.java`、`UserServiceImpl.java`、`DataSourceMessageSource.java`。

### 1.1 字段确认（按前端反馈逐条回复）

| 接口 | 后端确认 |
|---|---|
| `POST /app/Login/registerCode` body `{phone, password, platform:"h5"}` 不传 msg | ✅ 支持。当手机号已注册且 `password` 非空 → 走密码登录（SHA-256 比对，与 H5 一致） |
| `POST /app/Login/emailLogin` body `{emailName, password, isFirebaseEmail:"1"}` | ✅ 是「密码登录 / Firebase 验证码登录」入口 |
| `POST /app/Login/emailAuth` | ⚠️ **不是 `emailLogin` 的别名**。`emailAuth` 是「邮箱验证码即注册即登录」一步式（body: `{emailName, code, platform, ...}`）。web 端做"密码登录"用 `emailLogin` 是对的 |
| `GET /app/Login/sendMsg/{phone}/forget` | ✅ |
| `POST /app/Login/forgetPwd` body `{phone, pwd, msg}` | ✅ 字段名就是 `pwd` 和 `msg` |
| `POST /app/Login/sendEmailMsg?emailName=&type=2&language=` | ✅ `type=2` 为找回 |
| `POST /app/Login/forgetPassWord` body `{emailName, password, code}` | ✅ 字段名就是 `password` 和 `code` |

### 1.2 字段不统一（手机 `msg/pwd` vs 邮箱 `code/password`）

**确认是历史现状，本次不动**——多端共用，统一会破坏 H5/App 兼容。前端在自己的请求层抹平即可。

### 1.3 登录响应格式

统一走 `UserService.getResult()`，**token/expire/user/action 在响应顶层**，**不在 `data` 里**。前端按 H5 实现正确。

```json
{
  "code": 0,
  "msg": "success",
  "token": "eyJhbGc...",
  "expire": 604800,
  "user": { "userId": 12345, "userName": "...", "avatar": "...", "phone": "..." },
  "action": "login"
}
```

## 5. §5 视频 343MB 上传失败（bug 19）—— **后端代码不需改，运维事项**

后端栈：
- Spring `max-file-size: 10240MB`（10GB），不卡；
- 应用层 `/publisher/course/upload` 视频 500MB，343MB 通过；
- **瓶颈一定在 Nginx / 网关**。

请运维：
```nginx
server {
    client_max_body_size 600M;
    ...
}
```

如果走 Cloudflare Free，无法突破 100MB，需付费版或绕过 CF 直传 OSS。

排查时让前端把失败 XHR 的 `status` 抓给后端：
- 413 → 必是 Nginx
- 504 → 网关超时
- connection reset → 中间件断连

## 6. §6 结算中心（bug 21 / 22 / 23）—— 路径对齐 + 新接口

### 6.2 已有的（前端反馈说"待后端"，其实已有）

| 前端期望路径 | 后端实际路径 |
|---|---|

### 6.4 新增：结算单 + 申请结算（bug 22）

工作流：
1. **admin 端**按发行方+周期生成 status=0（草稿/可申请）的结算单；
2. **发行方端**在前端看到 status=0 列表，点"申请结算" → status=1（已申请待审核），同时落入当前收款账号快照；
3. 后续 status=2（审核通过）/3（已打款）/4（驳回）由 admin 端补完（v1 仅做 generate + apply，状态机预留）。

#### 6.4.1 发行方端

```
GET  /publisher/settlement/records?status=&page=1&limit=10
POST /publisher/settlement/apply         body { "recordId": 123 }
```

`status` 枚举：`0草稿 / 1已申请 / 2审核通过 / 3已打款 / 4驳回`（不传则全部）。

records 响应（标准分页）：

```json
{
  "code": 0, "msg": "success",
  "data": {
    "totalCount": 12,
    "list": [
      {
        "id": 123,
        "periodStart": "2026-06-01",
        "periodEnd": "2026-06-30",
        "grossUsd": 1250.00,
        "creatorUsd": 1000.00,
        "platformUsd": 250.00,
        "ratioLabel": "8:2",
        "status": 0,
        "auditRemark": null,
        "applyTime": null,
        "payTime": null,
        "payVoucherUrl": null,
        "accountSnapshot": null,
        "createTime": "2026-06-30 02:00:00",
        "updateTime": "2026-06-30 02:00:00"
      }
    ]
  }
}
```

apply 异常：
- `403317 结算单不存在`（含「不是自己的」也归此码，不泄露他人 id）
- `403318 结算单当前状态不可申请`（必须 status=0）
- `403319 未配置收款账号，无法申请结算`

apply 成功响应 `data` 是新状态的 record（status=1，accountSnapshot 已填）。

#### 6.4.2 admin 端（手动生成结算单）

```
POST /admin/publisher/settlement/generate
```

请求体：

```json
{
  "publisherUserId": 12345,
  "periodStart": "2026-06-01",
  "periodEnd": "2026-06-30",
  "ratioLabel": "8:2"
}
```

服务端自动按周期聚合 `publisher_earnings`：
- `grossUsd = SUM(gross_usd)`
- `creatorUsd = SUM(creator_usd)`
- `platformUsd = gross - creator`
- 周期内无数据则三个金额都是 0，仍会生成一条 status=0 的空单（便于操作记录）

异常：
- `403320 结算周期参数错误`（缺字段或 end < start）

### 6.5 bug 23「真实分润」

`publisher_earnings.creator_usd` 已经按当前 `publisher_revenue_config` 的 80%/60% 算（详见 `RevenueResolverService`）。**当用户真实付款后**：
1. 支付回调进 `publisher_earnings_log`（明细 + ratio 快照）；
2. cron 每日把昨日 log 聚合写入 `publisher_earnings`（gross + creator）；
3. admin 月底（或任意周期）按 §6.4.2 生成结算单；
4. 发行方看到列表后申请。

前端展示直接拿 `creatorUsd`（已扣分润）就是发行方实得，不需要再算。
