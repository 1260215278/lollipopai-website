# 前端反馈 · 发行中心账号与顶部信息缺口（20260704）

> 来源：按 `page-figma-design.md` 的「账号中心」3 张设计稿与 `docs/0703/发行中心-账号信息页UI小改-前端对接.md` 开发时发现。  
> 原则：字段不猜、接口不做撒网式 fallback；未确认的短信场景前端先不发请求。

## P0. `/publisher/account/sendSmsCode` 缺少 `scene` 枚举契约

### 现状

账号中心文档只写到：

| UI 元素 | 接口 | 备注 |
|---|---|---|
| 修改密码 | POST `/changePassword` `{oldPassword?,smsCode?,newPassword}` | 与 App 登录同一密码 |
| 两步验证-管理 | POST `/twoFactor/enable\|disable` `{smsCode}` | 先 GET `/sendSmsCode` 发码 |
| 注销账号 | POST `/cancel` `{confirm:true, smsCode}` | 守卫 `403341/403342` |

但没有说明 `GET /publisher/account/sendSmsCode` 的请求参数 `scene` 允许值、各值对应的验证码用途、错误码和频控口径。

### 前端影响

- `passwordSet=false` 时修改密码需要 `smsCode`，但前端无法确定发码 `scene`。
- 两步验证启用/关闭需要 `smsCode`，但前端无法确定启用和关闭是否共用同一个 `scene`。
- 注销账号需要 `smsCode`，但前端无法确定注销发码 `scene`。
- 现在前端只能展示入口与说明，不应猜 `scene=changePassword` / `twoFactor` / `cancel` 等字符串。

### 建议后端补充

请明确并固化如下契约：

```http
GET /publisher/account/sendSmsCode?scene=<scene>
```

建议枚举：

| scene | 用途 | 后续提交接口 |
|---|---|---|
| `change_password` | 未设置密码时，通过短信设置新密码 | POST `/publisher/account/changePassword` |
| `two_factor_enable` | 启用两步验证 | POST `/publisher/account/twoFactor/enable` |
| `two_factor_disable` | 关闭两步验证 | POST `/publisher/account/twoFactor/disable` |
| `cancel_account` | 注销账号 | POST `/publisher/account/cancel` |

同时请确认：

- 验证码发送到当前成员绑定手机号，还是发行账户主账号手机号。
- 当前成员未绑定手机号时返回的错误码和文案。
- `scene` 非法时返回的错误码。
- 发送频控、验证码有效期、重复发送是否覆盖旧码。
- `changePassword` 在 `passwordSet=true` 时是否仍允许 `smsCode` 替代 `oldPassword`。

## P1. 顶部账号信息展示字段不足

### 现状

设计稿顶部用户区展示类似：

```text
12****5674
出品方
```

`发行中心-播放数据-前端对接.md` 也说明页面顶部账号信息用已有 `GET /publisher/member/me`。

但当前前端可确认的 `GET /publisher/member/me` 契约主要是权限驱动：

```json
{
  "memberUserId": 10001,
  "role": 2,
  "roleName": "管理员",
  "permissions": ["dashboard", "course", "settlement_view"]
}
```

缺少顶部展示需要的手机号掩码、昵称、头像等字段。`/publisher/account/info` 虽然有 `profile/contact`，但文档注明账号信息接口仅超管可用，不能作为所有角色通用顶部信息来源。

### 前端影响

- 员工/管理员页面顶部无法稳定展示设计稿里的 `12****5674`。
- 如果前端改用 `/publisher/member/list` 找 `self=true`，会多拉超管列表接口，且成员列表接口并非所有角色都应可访问。
- 目前只能临时展示发行公司名或默认「发行者」，与设计稿不完全一致。

### 建议后端补充

建议扩展 `GET /publisher/member/me`，保持原字段不变，新增只读展示字段：

```json
{
  "memberUserId": 10001,
  "role": 2,
  "roleName": "管理员",
  "permissions": ["dashboard", "course", "settlement_view"],
  "nickname": "运营管理员",
  "avatar": "https://oss.example/avatar.png",
  "phoneMask": "12****5674",
  "publisherName": "北京星河文化传媒有限公司"
}
```

字段说明：

| 字段 | 类型 | 说明 |
|---|---|---|
| `nickname` | string | 当前登录成员昵称；无昵称时请返回可展示的账号名或空字符串 |
| `avatar` | string \| null | 当前登录成员头像 |
| `phoneMask` | string \| null | 当前登录成员手机号掩码，建议与成员列表 `phoneMask` 口径一致 |
| `publisherName` | string \| null | 发行方/出品方名称，用于用户菜单或顶部补充展示 |

## P2. 可选确认：成员 `add` 成功响应体

### 现状

`POST /publisher/member/add` 文档未写成功后 `data` 返回什么。前端当前只依赖 `code=0`，成功后重新拉 `GET /publisher/member/list`。

### 建议

不阻塞前端。如果后端方便，可返回新增成员实体，结构同 `GET /publisher/member/list` 单行：

```json
{
  "memberUserId": 10002,
  "nickname": "运营管理员",
  "avatar": null,
  "phoneMask": "139****6688",
  "role": 2,
  "roleName": "管理员",
  "status": 1,
  "statusName": "使用中",
  "self": false,
  "removable": true,
  "joinTime": "2026-07-04 10:00:00"
}
```

前端仍会兼容 `data=null`，这项仅用于减少一次列表刷新请求。
